# 开发流程

这份文档写给在本仓库工作的人：从接到需求到交付，再到每周回头归约，自己该做什么、判断什么。

机器已经守住的部分不在这里重复——Agent 的约束见 [AGENTS.md](../AGENTS.md)，交付前的五层自查见[交付前评审](../review.md)。本篇讲的是人走完整周期时的动作和判断点。

## 三个判断点

整条流程里需要人判断的只有三处，其余都应交给机器确认：

1. **要不要做这个需求。** 用户价值与边界以[产品定位](产品定位.md)为准。
2. **做出来的东西是不是想要的那个。** 对照需求本身，不是对照实现；证据以真跑为准，不以测试变绿为准。
3. **哪种返工值得变成规则。** 每周归约时判断，见下文。

除了这三处，任何"再检查一遍""再确认一下"都应该变成一条机器能执行的检查，而不是一次人眼复核。

## 四个周期

| 周期 | 触发 | 谁做 | 产出 |
|---|---|---|---|
| 一次改动 | 需求确定 | 人 + Agent | 分支、实现、验证结论 |
| 一次交付 | 改动完成 | 人 + Agent | PR、CI 结论、合入 |
| 一周 | 固定时间 | 人 | 最多三条机制化建议 |
| 一月 | 固定时间 | 人 | 规约与清单是否仍然成立 |

越往下，判断越少、间隔越长。周期的意义是让每周的返工变成下一周的规则，否则前面两层只是在更快地重复同样的返工。

## 一次改动

1. 按 [Git 协作约定](../AGENTS.md#git-协作流程)准备本次任务的基准、分支与 worktree。
2. 改之前先读[运行语义规约](架构/运行语义规约.md)：涉及状态归属、事实提交、异步身份或中断恢复时，先明确业务对象、所有者、写入入口和恢复依据。
3. 实现后按 [AGENTS.md 的验证表](../AGENTS.md#验证与交付)运行本次改动对应的统一入口。
4. 行为变化按 [verify-konden](../.claude/skills/verify-konden/SKILL.md) 在真实应用里取证据。`pytest` 变绿不证明页面行为。
5. 交付前按[交付前评审](../review.md)从结构层往下过一遍。能在低层拦住的错误，回去改代码，不带到高层靠说明绕过。

## 一次交付

提 PR 时写清三件事：改了什么、依据是什么、**哪些没有验证**。未验证范围是交付说明的一部分，不是免责声明。

CI 与评审意见由 Auto-fix 跟进；合入由人决定。参考原则：一次 PR 只做一件事，能拆开的独立改动不要挤在同一个 PR 里。

## 周归约

每周一次，目的是把这一周的返工变成下一周的检查。**这一步暂时由人执行，形态还没定，所以没有自动化**——先按下面的做法手动跑几轮，等什么该固定下来清楚了，再谈是不是做成例程。

### 取数

```bash
git fetch origin
git log origin/main --since="7 days ago" --oneline
git log origin/main --since="7 days ago" --pretty=%s | grep -E "修复|校准|对齐|回退|修正"
git log origin/main --since="7 days ago" --name-only --pretty=format: | grep -v '^$' | sort | uniq -c | sort -rn | head -20
```

### 归因

把每一条返工归入三类之一，三类都要能认出来；认不出"正常迭代"的归约，会把 UI 打磨也当成问题去治。

| 类型 | 判据 | 处理 |
|---|---|---|
| 可机器化 | 同一个错误在两处以上重复出现，且判据确定 | 写成规则或检查 |
| 设计层重做 | 同一能力反复重做，每次形态都换 | 先立接口，规则拦不住 |
| 正常迭代 | 同一文件反复改但方向一致（打磨、文案、样式） | 不处理 |

### 产出

最多三条建议，每条写清四件事：现象、证据（提交号或文件）、该落在[交付前评审](../review.md)的哪一层、用什么方式验证它确实被拦住了。

一条建议只有在"下次同样的错误能被自动发现"时才算机制化成功。否则它只是又一条散文。

建议由人决定做不做；做了就走上面"一次改动"的流程。

### 记录

归约结论留本地即可，原始数据属于一次性材料。只有被采纳的规则进入仓库。

## 月校准

每月一次，回答"我们定的东西还成立吗"：

- [交付前评审](../review.md)的五层是否还有该删或该加的条目；
- [运行语义规约](架构/运行语义规约.md)的四条不变量有没有被新的实现绕开；
- 对新出现的重复来源，核对[端点与地图引用](../tests/architecture/test_reference_consistency.py)、[前端请求](../tests/architecture/web_routes.py)和[文档链接](../web/tests/markdownLinks.test.ts)的实际检查范围，比较漏报与误报代价。

[CI](../.github/workflows/ci.yml) 在 PR 和主分支检查全部 TLA+ 模型。本地使用 Temurin JDK 21，运行入口见[验证表](../AGENTS.md#验证与交付)。每个模型的范围、检查性质与反例见 [formal 目录](../formal/)下的 README。

修改相关协议时，对照模型 README 更新动作、有限范围和公平性前提，重跑原模型及其指定变异，并记录状态数、耗时和反例。月校准时检查日落条件，机制移除或保证下沉后同步删去失去保护价值的模型。

## 判断：什么时候把错误下沉

一条经验值得从人脑搬到机器，通常满足两条以上：

- 它已经在两次以上的交付里被重复纠正；
- 判据是确定的，不需要理解上下文就能判断；
- 它现在的载体是散文、注释或某个人的记忆。

下沉的顺序固定：先立接口让错误写不出来，再写规则拦住，最后才靠证据和评审。顺序颠倒的代价是后面每一层都在替前面补漏。
