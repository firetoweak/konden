# 模型交互可靠性

2026-10-14、20、21 日及 2026-11-18 的记录显示：模型理解要求、表达意图与实际产出约定的工具或正文，是不同的证据。下面的观察来自不同任务与条件，不能合成一个成功率。

## 回答工具与实际可见性

当时给人回答必须调用 `message_user`，普通结尾只作为折叠工作记录。deepseek-flash 在一次真实应用观察的 16 次直接提问中只调用了 3 次回答工具；它仍可能认为普通正文已经回答了人。

隔离复现发现，说明可以改善新会话，却不能稳定纠正已经积累的回答习惯：

| 条件 | 回答工具调用 |
|---|---|
| 新会话先要求只回复 PING_OK，再追加可观察行为说明 | 两次均为 20/20 |
| 已积累五轮纯文字回答，再在系统角色追加说明 | 8/16 |
| 同一批继续，将说明放到用户角色 | 12/16，仍有一个 Bot 完全不用 |

最后一行是同批续跑，不是独立的角色优劣对照。其他新会话运行也有明显波动，不能把某次全成功当作稳定保证。

当时的选择是让普通回复与人的实际可见性一致，减少协议形态与交互含义的错位，取舍见[交互与响应](../架构/多智能体/交互与响应.md#普通回复给人协作消息显式发送)。原试验只测了该模型和人直接提问，没有验证其他来源开始的工作。

## 短对话协议：新会话与旧历史切换

2026-11-18，在 `origin/main@a1b7e11e` 上用真实 `deepseek/deepseek-flash` 比较四种条件，每组五个会话、每会话二十条输入，共四百条输入。样本在会话内连续积累历史，不能当作四百个独立试验。系统提示只在会话开始或切换契约时设置，不逐条提醒调用工具；没有为未发送的回答追加提醒、补发或重跑。

这是隔离的模型协议实验：输入为合成对话，`send_message(recipient, text)` 的本地收信器记录通过参数校验的发送。普通直出组把普通正文计为给用户的消息；显式组只有工具实际发送才算交付，普通正文允许作为未交付的工作记录，不要求空结尾。用户、同事和群的可选身份明确列在工具参数里。实验没有修改产品规则，也没有接入真实同事或向产品会话发消息。

| 条件 | 预设 | 实际结果 |
|---|---|---|
| 普通回复直出对照 | 一百条私聊输入均答复用户 | 一百条均有用户收信记录 |
| 新会话统一显式发送 | 相同的一百条私聊输入通过工具答复 | 九十九条实际发送，一条纯记忆输入未发送 |
| 五轮普通回复历史后切换到显式契约 | 保留真实旧历史，替换系统提示后再处理二十条输入 | 一百条均只写普通正文，发送调用及用户收信记录均为零 |
| 新会话混合来源 | 七十条应发送，其中用户五十条、同事十条、群十条；三十条应安静结束 | 七十条均发送给预设对象，三十条均未发送；未观察到错送或重复发送 |

极简输入包含“你好”“在吗？”“1+1等于几？”以及日常交流；混合组交替放入用户私聊、群报告、同事请求、例行检查及需要用户决定的事项。已知答案只做字面核对，闲聊只核对是否实际发送，不据此声称完成了开放式回答质量评测。

新会话唯一未发送的是“先记住，我叫小林，喜欢蓝色”。模型的普通正文说明它按“不发纯确认”结束，与“用户私聊交流应答复”的预设存在契约歧义，不能据此认定忘记调用发送工具。其余九十五条明确应答输入均实际发送，五条纯记忆输入中四条发送。原始评分仍保留这一条未发送，没有事后改成通过。

旧历史切换组则包含明确反例：“在吗？”只得到普通正文“在。”，“1+1等于几？”只得到普通正文“2。”，均没有发送调用。去掉五条纯记忆输入，仍有九十五条明确应答输入未发送。为排查附加字段影响，另取相同五份旧历史，只删除旧助手消息的 `reasoning_content`，保留正文、工具和新系统提示，分别重复前四条输入，共二十条；仍全部只写正文、没有发送调用。这个小对照说明本次失败不能单独归因于旧推理字段，没有证明所有模型或历史都会如此。

这组结果说明仅替换提示不足以让这批旧会话可靠切换。新会话的短对话结果不能证明复杂任务可靠，后面的公开任务已经出现新会话漏交付。尚未验证其他模型、完整生产提示和能力目录、压缩后的历史，以及真实界面、持久投递与恢复；本地收信回执不能替代这些验证。

原始请求、普通正文、工具调用、收信记录、冻结提示、脚本哈希与一次性脚本留在本任务 worktree 的 `.tools/explicit-delivery/`；主实验为 `results-20261118/`，附加字段对照为 `probe-text-history-20261118/`，结果截图位于 `evidence/`。

## 公开 Agent Benchmark：业务对话与终端长任务

2026-11-18，使用同一真实 `deepseek/deepseek-flash`，在公开任务上成对比较普通回复直出与统一显式发送。任务、业务环境和原始评分器保留；自定义 Agent 适配器衔接模型调用与交付契约。显式组只有合法的 `send_message(recipient="user", text=...)` 才有收信记录，普通正文不转发；没有漏发提醒或自动补发。修正适配与提示歧义后运行完整成对批次，不从不同批次择优拼接。本次验证直接任务中的必要沟通，不验证群内报告是否值得再私聊通知。

这不是完整 konden Runtime 的端到端验证，也不是官方榜单成绩。两组温度均为零，未强制模型采样种子；下表正式对照每个任务每种契约各一次，适配与环境错误的先导运行另列。这些子集不能估计全量任务或生产流量的成功率。任务完成得分、模型实际交付的消息、执行长度分别统计，模拟用户的工具和模型调用不算 Agent 的工具链。

### τ²-Bench

固定 [τ²-Bench v0.2.0](https://github.com/sierra-research/tau2-bench/tree/v0.2.0)，提交 `f8de30c298689cbe0117d76a378e7315a17e5bd8`。推理前按参考动作数降序、任务 ID 字典序，分别选航空、零售、电信四个任务，共十二个；参考动作只用于选样，不提供给模型。使用原始 Orchestrator、模拟用户行为及 `EvaluationType.ALL` 评分，保留数据库、沟通和环境断言检查。基准的固定开场语两组相同，不计作模型发送。Agent 与模拟用户都使用上述 DeepSeek 模型，环境种子为 300，每次最多二百个原生编排步骤。

正式对照在两组模型可见提示中，都将“工具调用与回复互斥”里的工具明确为业务工具；显式发送是消息传输，不能与业务动作在同一轮混用。只有这条通信术语和发送形式经过适配，身份核验、用户确认、业务权限和任务目标不变，基准源文件没有修改。这避免把原始“调用工具时不能回复”的措辞与发送工具叠加，制造协议冲突。

| 契约 | 官方 reward 为 1 | 必要正文未交付便结束 | Agent 最多业务工具调用 | 两次客户消息之间最长业务工具链 |
|---|---|---|---|---|
| 普通回复直出 | 8/12 | 0/12 | 30 | 26 |
| 统一显式发送 | 2/12 | 9/12 | 19 | 10 |

逐条核对显式组的九份未交付正文，都是需要用户回复的信息：八例在首次业务工具前，把身份核验等必要追问写成普通正文；另一例航空 42 已成功发送一次，并执行九个业务工具，随后请求用户选择保留、取消哪些预订，却没有再次发送。它们是新建基准会话，除相同的固定开场语外没有旧问答历史。适配器记录未交付结束，不把正文传给模拟用户，再交给原始评分器评估。

显式组两个 reward 为 1 的任务也必须区分：航空 41 零业务工具、零发送，只把含 `recipient`、`text` 的 JSON 写在正文里；目标数据库状态允许保持不变，且没有必须沟通的信息条件，因此这个官方通过不能计为消息交付成功。另一例电信任务实际发送十三条、执行八个业务工具并通过。航空 39 则发送四条、执行十九个业务工具，业务评分仍失败，普通直出对照也失败，不能将所有业务失败都归因于漏交付。

普通直出最长原生轨迹为 109 条消息，包含双方工具与回复；Agent 最多 26 次模型调用，双方合计最多 73 次模型调用，单次 Agent 输入最多 25,529 tokens。109 条轨迹消息和 73 次双方模型调用均不等于百次工具链。

### Terminal-Bench

固定 [Terminal-Bench v4.1.0](https://github.com/harbor-framework/terminal-bench/tree/v4.1.0)，提交 `4070d6cef56a7d20cb5dc98d5e10ada88a6b9440`，使用 Harbor 0.26.0 的原生 Trial。推理前选定 `session-window-debug` 2.3.0 与 `wal-recovery-ordering` 2.5.0，分别涉及流处理状态修复与 WAL 恢复、并发提交；使用原始任务说明、Docker 环境、资源限制、隐藏测试及独立验证容器，不向 Agent 提供评分器或参考解。

任务原定 Agent 上限均为八小时，本地成对实验将模型执行预算缩为三十分钟、最多二百次模型决策；保留原始验证器时限。这是缩短预算的子集实验，不能作为原预算下的标准成绩。模型使用真实 shell 读写代码并运行检查，没有模拟等待、填充历史或人为要求凑满调用次数。累计工具数统计实际 `execute` 调用，连续工具链另按两条已交付消息之间的调用数计算，发送工具不计入业务工具数。

| 任务 | 契约 | 官方 reward | shell 累计（最长连续） | 最大单次输入 tokens | 末次工具后有用户结果 |
|---|---|---|---|---|---|
| session-window-debug | 普通直出 | 1 | 46（34） | 113,532 | 有 |
| session-window-debug | 统一显式 | 0 | 39（39） | 100,784 | 无 |
| wal-recovery-ordering | 普通直出 | 0 | 54（54） | 115,926 | 有 |
| wal-recovery-ordering | 统一显式 | 0 | 45（45） | 110,209 | 无 |

四次模型执行分别为 634.422、589.969、616.266、603.735 秒，均自然结束。两次显式运行都没有任何发送记录，末轮却有面向用户的修复总结；这是漏交付，不能解释为没有新信息而安静结束。“有用户结果”也不代表修复正确：流处理任务隐藏检查分别通过 9/9、7/9，WAL 两组都通过 95/97，官方 reward 按原规则分别为 1、0、0、0。

这批实际覆盖到五十四次连续工具调用和约十分钟的模型执行，不能声称覆盖百次以上工具链或多小时执行。成功返回的单个 shell 调用最长为 31.656 秒，四次正式运行都没有工具等待超时，因此也没有验证数分钟的单工具等待、超时后交付、中断与恢复。

### 先导运行、评分故障与结论边界

未澄清通信术语的 τ² 批次原样保留：普通直出 9/12 官方通过，显式 1/12，十一例只写正文结束；因为存在原始工具规则与新传输形式的歧义，不与正式对照合并，也不把差值归因于某一个提示改动。

终端另外四次先导运行也单列：流处理普通组在第七次工具调用遇到 120 秒等待超时，适配器未处理 Harbor 的已知异常，未得到有效评分；流处理显式组执行四十一次工具并发送结果，原始产物重评 reward 为 0；WAL 普通组执行四十次并发送结果、显式组执行四十一次但未发送，reward 均为 0。先导显式发送有成功也有失败，不用其中较好的运行替换正式结果。

Windows Git 的 CRLF 转换曾使官方 `test.sh` 无法启动；将所选任务六十八个文件恢复为 Git 原始字节后逐个核对一致，未修改任务或评分逻辑。另有验证镜像依赖下载超时。正式流处理显式轨迹因此仅用 Harbor 原生 regrade 重评保存产物，得到 7/9 检查通过、reward 为 0，没有重跑模型；原错误及重评来源均保留。这些适配、换行和下载错误不算作模型能力失败。

公开任务复现了必要追问、任务中途选择以及长任务结果的漏交付，说明前面的短对话结果不足以支持统一显式发送在当前模型上可靠。它们没有证明工具链长度导致漏发，也没有证明所有模型都会如此。是否值得打扰用户、真实 konden 提示与能力目录、持久投递和界面可见性，以及百次工具链和长时间工具等待，仍需分别验证。

原始请求、原生轨迹与评分、收信记录、冻结适配器及哈希、版本和依赖记录留在本任务 worktree 的 `.tools/public-agent-bench/`。正式结果为 `tau-results-v3-20261118/`、`terminal-results-v2-20261118/`；原生重评为 `terminal-regrades-20261118/`，其他批次保留作先导与故障记录。汇总从原始评分和逐次调用记录重新计算，截图及汇总审计位于 `evidence/`。

### 加入可回答的 `ask_user` 后重跑 τ²-Bench

2026-11-18，在 `main@5f01d292` 上，用同一 DeepSeek Flash 模型重跑上述十二题。两组都使用该版本的 `ask_user` 工具定义、卡片提示和问题格式化逻辑。普通直出组保留面向用户的文本回复。显式组的必要追问可走卡片，其余客户消息通过 `send_message` 投递。每题每组各跑一次，沿用原始业务环境、模拟用户场景与评分器。

模型发卡后，本轮结束。模拟用户看到问题和全部选项，按原任务独立作答，可以选其他方案、自由回答，电信用户也可以先检查设备。适配器按问题 ID 关联答案，将原问题和答案一并放入下一轮模型输入。未发出的正文不交给模拟用户。逐张核对模型的工具调用、用户实际收到的内容、原生轨迹中的回答和下一次模型请求。

| 私聊交付方式 | 用过卡片的任务 | 发卡后收到回答并继续 | 必要追问未交付便结束 | 官方任务通过 |
|---|---:|---:|---:|---:|
| 普通回复直出 ＋ 澄清卡片 | 9/12 | 16/16 张 | 0/12 | 7/12 |
| 显式发送 ＋ 澄清卡片 | 9/12 | 15/15 张 | 9/12 | 2/12 |

正式运行共发出 31 张卡片，其中 15 张带选项，其余为开放式问题。显式组有三题首轮将身份核验问题只写进正文；另六题已成功发卡、收回答并继续，之后把必要确认或追问只写在正文便结束。例如航空 44 先用卡片拿到用户 ID，连续执行 26 次业务工具，算出三笔升舱共需补 1,387 美元，随后在私有正文里询问是否同意并追问取消原因。用户没有收到这次请求。

与上一批逐题对照，两批显式组各有九题漏发，其中七题重合。航空 41、42 在新批次完成了沟通，另外两道电信题这次出现漏发。航空 42 的模型先后三次使用卡片，分别核验身份、取得用户选择和确认，最后显式发送了取消结果。其余两个没有漏发的显式任务也交付了结论或转人工通知。单次成对运行能定位这些差异，不能据此估计增加工具对总体成功率的影响。

另在独立数据目录启动该版本的 Web 后端和真实模型，通过 Web 回答接口回放零售 30 独立预跑里的一条自由回答。Bot 出示“换其他型号／退货”卡片，按原问题 ID 提交用户要求改为退货的英文原答后收到 HTTP 200，重新读取会话得到相同答案。Bot 下一轮复述“你选择的是退货，不换其他型号”。这一次验证了实际接口及会话续接，未计入基准分数；其余二十四条轨迹使用基准适配器。本轮未重跑终端任务，也未验证自主群聊工作何时值得私聊通知。

逐题原始记录与冻结适配器位于 `.tools/public-agent-bench/tau-results-v4-20261118/`，独立预跑位于 `tau-card-preflight-20261118/`。同目录下的 `evidence/card-audit.json`、`evidence/live-card-route.json` 和 `evidence/cards.jpg` 分别记录交付核对、Web 接口往返及关键截图。

模拟用户对 GPT 的 186 张卡片全部给出了文字回答。三条答复同时带有基准结束标记 `###STOP###`，原编排器在把答案传给 Agent 之前结束了会话。零售 4 的显式组因此停在客户已确认修改两件商品的时刻。另外两例是电信客户确认彩信已经发通。独立续跑逐次校验并重放原请求和响应，保留每条自由回答，只移除末尾标记，让 GPT 收到原问题和原答案。零售 4 随后执行两次订单修改并显式发送结果，续跑评分为 1，正式批次保留原分 0。

这批结果也能区分交付可靠性和打扰频率。GPT 普通组交付了 107 条客户可见消息，显式组交付了 116 条，其中 96 张卡片、20 条 `send_message`；单是四道电信排障题就用掉了显式组的 72 张卡片。没有观察到显式交付减少本批直接会话的可见消息数。主动后台工作是否该通知用户、一次私聊是否可以少问几轮，仍需分别衡量。

### 同一份群报告，换一个通知约定

2026-11-18，在 `main@5f01d292` 上从三条 τ² 任务轨迹中各取一份报价，改写为中文群报告。航空升舱共增加 1,387 美元，零售换款增加 0.26 美元，电信流量增加 4 美元。每份报告保持不变，只替换用户先前的私聊约定。六种情形各用独立会话重复三次，两种模型共 108 轮。通知约定、预算和评分都是本地实验设计，运行前已固定。

| 用户的约定和实际情况 | 期待的私聊行为 | DeepSeek Flash 符合 | GPT-6.1 Sol 符合 |
|---|---|---:|---:|
| 完整报告放群里就好 | 不私聊 | 9/9 | 9/9 |
| 查完私聊最终增加的总额 | 私聊正确总额 | 9/9 | 9/9 |
| 仅超预算才问，实际低于预算 | 不私聊 | 9/9 | 9/9 |
| 仅超预算才问，刚好等于预算 | 不私聊 | 9/9 | 9/9 |
| 已超预算，需要用户决定是否提高 | 发决策卡片 | 8/9 | 9/9 |
| 已超预算，只要求告知超出多少 | 私聊正确差额 | 9/9 | 9/9 |

DeepSeek 唯一一次漏发是电信报价 4 美元、预算 3 美元。模型同时调用群发送和需要独立调用的 `ask_user`，整批被拒，两个动作都未送达。实际发出的 17 张卡片均由模拟用户回答，逐条核对了下一次真实请求中的原问题和答案。17 次都按要求只回原群，其中 16 次明确传达了用户的决定。剩余一次 DeepSeek 把 0.26 美元写成“在预算内”，省略了用户刚同意把预算从 0.25 提至 0.26 美元。

两种模型在应免打扰的 27 轮中都没有私聊。检查同一批次的群记录，DeepSeek 在全部 27 轮回了群，GPT 在 22 轮回了群。即使用户只说“完整报告放群里就好”，报告已经在群里，DeepSeek 仍有 9/9 轮回帖，GPT 有 4/9 轮。预算情形中，群唤醒提示允许补充新内容，核算是否在预算内也可能有价值。这一计数说明私聊可以安静，判断群消息是否多余仍需看内容。

在确实应发普通私聊的 18 轮中，两种模型均送达了用户要求的金额。DeepSeek 另有 9 轮同时在群中发言，GPT 有 0 轮。

实验复用了产品的群事件、群发送工具及澄清问答格式，用实验性的显式私聊工具和隔离收件箱记录投递。结论限于约定明确、报告已齐的短会话。完整生产调度、长上下文中找回旧约定和多个 Bot 连续响应群消息均未在本批验证。逐次请求、回执与审核留在本 worktree 的 `.tools/public-agent-bench/group-notice-v2-20261118/`，汇总截图在 `.tools/public-agent-bench/evidence/group-notice.jpg`。

## 协作约定与空结尾

另一组 deepseek-flash 实验创建三位无项目 Bot，依次说明分工、请求同事查已知或未知信息，再在群里讨论。对照组与加入协作约定的组各运行两次：

| 准备阶段 | 对照两次 | 加入约定后两次 |
|---|---|---|
| 工具调用 | 64、55 | 11、10 |
| Bot 间私信 | 16、9 | 0、0 |

约定减少了没有任务依据的寒暄、分工讨论和环境探查。一次对照中，Bot 把关于群记录的提示读成自己应已在某个群里，转而查找配置与数据库；修正措辞后，这类自发工作基本消失。给人的回复更短，但条数没有稳定下降。

随后允许长期 Bot 用空响应结束无需回答的一轮，追加两次运行。两次均没有实际空结尾；有的 Bot 在思考中明确判断“应该沉默”，最后仍输出一句说明。这个试验只说明该模型在这些场景下不能可靠地产出空结尾，不证明更强模型也做不到。

四次原协作运行没有出现把同事回答只写成普通回复的情况。不能因此认定显式工具一概可靠：回答人、回复同事与保持沉默是不同任务，例行任务场景也未测。

## 承诺不等于执行

2026-10-14，stepfun/step-5-preview 被要求连续安装两个 Skill。第一个成功后，模型说马上安装第二个，随后没有提交工具调用。

事实核对确认：安装结果已请求下一次决策，模型也已执行该决策，安装工具仍可见，返回却只有行动承诺。因此本例是“得到执行机会但未调用”，不支持“没有唤醒”或“工具不可用”的解释。

模拟模型与确定性测试能够连续走通两次安装，但这不证明真实模型必然持续执行。该记录只有一个样本，不能确定频率或归因；持续任务静默停下的问题也没有被前两组实验解决。

这些观察支持分别检查输入是否送达、能力是否可见、模型是否实际行动，以及人是否真的看到输出。不能从承诺文字补猜任务状态，也不能让 Runtime 据此替模型选动作或无条件重复唤醒。
