# 群聊与私信长程实验

2026-11-04，在三人和四人团队的连续任务中，观察到一次明确的“答案已写出，但没有发送给请求它的同事”。模型把上一阶段的交流限额理解为仍在生效的私信通道限制，新请求的答案因此只显示在用户私聊里。

同时，已经成功发送的 153 条群发言、41 条同事私信全部能与正式记录和收件方副本对应，没有发现这部分消息丢失或重复。**发送后的可靠性与模型实际发起发送，是两项不同的保证。**

本次是两条长程协作轨迹，不是独立重复抽样，不能用“1 / 模型调用次数”估计漏发概率。

## 条件与任务

基线为 `origin/main@824087b8`，Windows 隔离 Web、真实 Host 和 Worker，模型为已有配置的 `deepseek/deepseek-flash`，压缩阈值 500000 tokens，未显式设置推理档位。模型连接与主数据目录隔离，没有替换模型响应、伪造发送工具或改动生产协议。

三人分为统筹、容量、验收；四人另设成本成员。两组使用不同 Bot，持续保留各自历史，后续阶段不换会话。任务是合成的三城活动迁移发布推演，分散下发容量、时延、预算、准备时间和回滚要求，要求成员交换证据、找反例并修订方案，不执行真实发布。主任务从两个群页面发送，后续阶段经同一应用的 HTTP 入口驱动；页面展示抽样核对，投递记录全量核对。

| 阶段 | 协作要求 |
|---|---|
| 准备 | 各自在用户私聊说明职责，等待任务 |
| 1 | 汇集各自掌握的证据，给出初版方案和缺口 |
| 2 | 提高峰值、增加迁移窗口限制，重新计算并反驳 |
| 3 | 单独通知容量成员：Y 增量从 50 改为 35；要求与验收私信核对，再将共同结论带回群 |
| 4 | 群中更正共享资料、核对出处并发布修订版 |
| 5 | 预算降到 21、时延门槛放宽，比较单资源方案 |
| 6 | 验收私信统筹或成本，请对方独立核算 X、Y 两档费用并私信答复，暂不进群 |
| 7 | X 准备失败，结合已有证据作最终发布判断 |

没有把工具名写进每道任务。阶段 2 起以任务要求限制发言长度和次数；这不是系统硬保证，实际仍有超出约定的讨论。产品既有的讨论轮数、回应量、源头消息量限制均保留，通过新阶段继续积累历史，没有把连续 60 条消息称为 60 个调度轮次。

准备阶段也没有被人为擦除：三人组自主发了 1 条群消息，四人组在收到“等待任务”要求后仍展开了 40 条群讨论。因此两组历史长度不同，不能据此判断四人比三人更可靠或更不可靠。

## 全程结果

下表包含准备阶段和七个任务阶段，不包含之后的定向诊断。

| 观察量 | 三人组 | 四人组 |
|---|---:|---:|
| 真实模型调用 / 已提交决策 | 194 | 308 |
| 其中准备阶段 / 任务阶段 | 12 / 182 | 107 / 201 |
| 群消息总数（含人的阶段任务） | 60 | 103 |
| Bot 成功群发言 | 55 | 98 |
| Bot 成功同事私信 | 27 | 14 |
| 模型非空普通正文 | 98 | 201 |
| 群发送被限额拒绝 | 6 | 16 |
| 私信发送被限额拒绝 | 3 | 4 |
| 私信引用无效被拒绝 | 2 | 0 |

共 502 次真实模型调用，其中准备阶段 119 次、任务阶段 383 次。输入累计 34780862 tokens，其中缓存输入 28447232；输出 376250 tokens。这是长期上下文反复参与调用的累计用量，不是独立信息量。服务日志中的成功调用数与已提交决策数一致，没有观察到模型调用错误。

四次明确安排的双向私信核对中，三次在该阶段闭环，一次未回信。两组阶段 3 都将 C-17 更正经私信核对后带回群；四人组阶段 6 完成了独立成本核算往返，三人组阶段 6 出现下面的漏发。这个“3 次闭环、1 次未回”只描述这两条相关历史，不能解释为稳定的 25% 漏发率。

## 关键反例：新请求沿用了旧限制

以下时间均为北京时间。

20:16:08，三人统筹给验收的一次旧交流发送得到 `ORIGIN_LIMIT_REACHED`。随后阶段 5 停下。

20:16:26，用户在验收的会话布置一项新核算。20:16:31，验收成功私信统筹，明确要求独立计算两档费用并“数字和依据私信回复我就行，这次先不公开”。统筹收到该消息并进入模型判断。

20:16:39，统筹已经算出 X 为 `12 + 9 = 21`、余额 0，Y 为 `12 + 6 = 18`、余额 3，但只产生普通正文，开头是：

> 验收让我私信回两档账，但我给验收的私信通道已经达到上限，这条送不出去。数算好了，先放在你这里：

这一决策没有 `send_message` 调用。阶段结束时，验收的记录只有成功发出的核算请求和等回信的普通收尾，没有收到该答复。它不是一次发送被拒绝，也不是发送后的副本缺失。

核对事实发现，新请求与旧拒绝来自不同的交流起点；新请求当时只计入验收发出的 1 条消息，远低于 20 条限额，入站私信的跳数为 0。现有规则也没有针对这两人的持久通道禁用。模型在普通正文中把旧拒绝解释为仍然无法私信，这是本次漏调用的直接可观察表现。

证据对应 `step_b6f3e412621a488ebea376421f75b1e1`，请求为 `message-5901c1153ac0316badad1396f51392d8752105db543346e7c36f72722b013a9d`。原始正文、触发事实、发送结果和收件方记录均保存在本地证据中。

正式观察冻结后，另给统筹一次自然语言的新请求，要求现在将这笔账直接私信验收，没有修改 Prompt、工具或历史。20:19:59，它实际调用了发送工具，验收收到答复，之后双方继续核对。这段诊断新增 9 次真实调用、4 条成功私信，单独记录，不计入上表，也不将事后补发算作原阶段成功。

该对照支持“旧拒绝被泛化为持续限制”的定位；没有做提示措辞 A/B，不能断言唯一原因或认定追加提醒能稳定修复。

## 其余投递与普通正文

153 条成功群发言逐条对应群正式记录及全部其他成员的 404 份副本；41 条成功私信逐条对应指定收件人的唯一副本。未发现这部分消息缺失、内容或对象不符、重复入群。299 条模型普通正文的内部交付均完成，去向是对应 Bot 与用户的私聊。

另外 29 次发送被交流或讨论限额拒绝，2 次因私信引用无效被拒绝。这些是有明确返回的未送达，不能与“模型没有调用发送”合并为丢包率。三人组阶段 1 的最终执行修订、四人组部分预算修订在限额后只向用户展示，说明群内协作会在最后修订尚未共享时停下。

普通正文也不能一概计为漏发。大量内容是已发群结论的复述、等待或无新信息的收尾；同时有只发工具和正文伴随工具两种行为。将这些正文全部自动转进群，不能由本次数据证明是正确的交付规则。

## 验证边界与后续判断

启动及收尾 Doctor 通过，构建后的真实 Web 完成页面发任务和消息展示核对；全量成功发送的正式记录、收件方副本和普通正文交付核对通过。两组在冻结时均已静止，无待授权和 Worker 失败。本次只新增历史记录，生产代码与路由未改；没有运行生产代码 CI，也不将消息事实核对当作任务方案正确性的验收。

没有验证其他模型、跨上下文压缩、重启恢复、网络故障或其他操作系统，没有得到可泛化的漏发概率。任务中的发言次数约定还影响了部分成员是否继续共享，因此这些按约定延后的内容不算无意漏调用。

下一步优先检查限制契约的可理解范围：模型应明确知道哪一条可见请求引起的往来受限、哪些发送不能重试，以及新的请求仍可怎样处理，而不需要猜测内部计数。然后复用长程任务验证该调整，另行对照普通回复目标的设计。此次实验足以否定“显式发送天然不会漏”，尚不足以决定把所有普通正文自动回送群聊。
